# Verbly — engineering findings, 2026-09-05 (full report)

This document is self-contained: it records everything produced during the
2026-09-05 evaluation sessions — the implementation of the owner's work order
("Measurable and straightforward to produce right now.docx"), all engineering
measurements with their raw numbers, the latency optimization round with
per-fix effect isolation, the Phase 10–12 reachability proof, and the "Ife"
advancement diagnosis. It is written to be readable without access to the
repository.

**Project context.** Verbly is a web application (Next.js 15 App Router,
Tailwind + shadcn/ui, Supabase Postgres/Auth/RLS, deployed on Vercel) guiding
caregivers of non-verbal children through a 12-phase communication curriculum.
Its "RL" (Reinforcement Loop) is a **deterministic, curriculum-authored rules
engine — not machine learning**: fixed-threshold branching logic (75% pass
mark × 3 consecutive passes to advance a phase; retake/simplify branches; an
Age-Bracket Transition three-gate rule; a Communication Compass onboarding
assessment for initial phase placement). Clinical content (curriculum, Compass
item bank) is versioned data, not code. This is a master's dissertation
project; the measurements below feed its engineering-evaluation chapter.

**Infrastructure.** Vercel functions (originally region iad1 / US-East,
now dub1 / Dublin — see Part 3) + Supabase in aws-eu-west-1 (Ireland).
"Local" measurements ran a production build (`next start`) on the development
Mac against the same hosted database.

### 2.1 Cyclomatic complexity (target: M ≤ 5)

Measured with ESLint's `complexity` rule at threshold 0 (reports every
function) across `lib/engine/`.

- **64 functions total; median M = 2; 48/64 (75%) meet M ≤ 5.**
- Every exception is annotated in `complexity-report.md`. The two largest:

### 2.4 End-to-end latency (claim: < 15 ms) — and the optimization round

This became the largest finding of the day; full detail in **Part 3**.
Summary of the final state:

- Decision logic alone executes in **sub-10 µs** (measured previously —
  pure functions, no I/O).
- Full deployed HTTP round trips, after the two fixes in Part 3:
  **start 579 ms p50 / 906 ms p95; complete 715 ms p50 / 1,553 ms p95;
  check-in sync ~170 ms** (bound by the client's own network RTT, not the
  server).
- **The < 15 ms claim is not supportable as an end-to-end figure and should
  be restated.** Recommended framing: *"decision logic executes in
  microseconds; full server round trips complete in ~0.6–0.7 s at p50 on
  free-tier infrastructure, with the highest-frequency call (the check-in
  sync) at ~170 ms, dominated by the client's own network RTT."*
  (Before the optimization round the honest number was 1.2–2.2 s p50 —
  see Part 3 for the before/after.)

## Part 3 — The latency investigation (owner-directed second pass)

### 3.1 The owner's observation

Baseline local and production latency were nearly identical (start:
1,052 ms local vs 1,239 ms prod p50; complete: 2,355 ms vs 2,219 ms),
implicating **sequential database round trips** — which cost the same
wherever the server sits — rather than the Vercel(iad1)↔Supabase(eu-west)
region mismatch the first report had emphasized. This was tested by fixing
both independently and measuring each in isolation.

### 3.2 Call-sequence audit of the session routes

Every `await` on a Supabase read is a full network round trip from the
function to the database's REST layer (PostgREST over HTTPS).

**`POST /api/sessions/start` — was 6 sequential round trips** on the common
path:

1. `auth.getUser()` (Supabase Auth)
2. RLS-scoped child read (authorization)
3. Curriculum content read (the session row + version-pinned script)
4. Last-completed-attempt read (Simplified-variant gate)
5. Latest scored assessment read (readiness gate)
6. `session_instances` insert

Reads 1–5 key off the request body alone — **fully independent** — and now
run as one `Promise.all` batch. **Common path: 2 round trips** (batch +
insert). The readiness-gated first-session path adds a phase-sessions read,
then a parallel pair (completed-in-phase count ∥ readiness result): **4 round
trips, was 8**.

**`POST /api/sessions/complete` — was ~14 sequential round trips** on the
common (non-advance) path. Now **7**:

1. **Batch A** (independent): `auth.getUser()` ∥ RLS instance read ∥
   check-ins read
2. **Batch B** (all keyed on the instance row): session content ∥ full
   completed history ∥ prior-approximation attempts (only fetched when the
   session recorded Phase-12 approximation bonuses)
3. Phase-map read (needs history's session ids — genuinely dependent)
4. Outcome write (`outcome`, `score_percent`, `completed_at`)
5. **Age-bracket batch 1**: child row ∥ recent-sessions window ∥
   last-bracket-transition (all keyed on child id)
6. **Age-bracket batch 2**: window check-ins ∥ cooldown count
7. **One merged instrumentation update** — `age_gate_evaluation` and
   `downward_advisory` target the same row and were two separate updates;
   now a single update

**Dependencies deliberately kept sequential** (ordering carries meaning):

- The outcome write lands **before** the age-bracket evaluation — the
  evaluation's window and cooldown count read completed sessions, which must
  include the session being closed.
- On phase graduation: `phase_history` is written **before**
  `children.current_phase_id` moves — the audit-trail row must exist before
  the child's state changes (never a moved child without the audit row).
- The graduation path's next-phase read precedes both writes.

Two robustness details: the RLS-scoped reads retry once sequentially if the
parallel read races a token refresh (the middleware refreshes the session
cookie on every request, so this is rare); and the age-bracket window is
over-fetched 3× unfiltered and filtered in memory to the current bracket —
safe because instances are stamped with the child's bracket at `/start` and
the single-active-session rule means at most one in-flight session can
straddle a bracket transition.

Every status code, error message, and response shape is unchanged. 109 unit
tests pass; typecheck clean; database inspection confirmed the merged update
still persists both jsonb columns.

### 3.3 The region fix

Supabase is in **aws-eu-west-1** (visible in the pooler hostname). Vercel
functions defaulted to **iad1** (US-East). `vercel.json` now pins
`"regions": ["dub1"]` (Dublin — same region as the database).

### 3.4 Effect isolation — the headline table

Same measurement script for every configuration (a real caregiver account and
child created via the service role, sessions run through the real HTTP API
with genuine SSR auth cookies, 10–12 cycles, warm-up excluded, 10 of 20
planned check-ins recorded per session). All values **p50 / p95 ms**:

| Configuration | /sessions/start | /sessions/complete | compass score (single) |
|---|---|---|---|
| **Baseline**: sequential code, functions in iad1 | 1,239 / 2,746 | 2,219 / 3,061 | 1,668 |
| **Fix 1 only**: parallelized reads, still iad1 | 1,007 / 1,744 | 2,129 / 4,038 | 1,663 |
| **Fix 1 + Fix 2**: parallelized + functions in dub1 | **579 / 906** | **715 / 1,553** | **657** |
| Local `next start`, sequential (baseline reference) | 1,052 / 1,260 | 2,355 / 2,503 | 1,576 |
| Local `next start`, parallelized (reference) | 647 / 1,254 | 1,450 / 2,562 | 1,660 |

Check-in sync stayed ~160–176 ms in every configuration — it goes directly
from the client to Supabase's REST layer, so neither fix touches it; it is
bound by the client's own RTT to eu-west.

### 3.5 Interpretation

- **The owner's diagnosis was correct that sequential round trips dominate —
  but the two costs multiply, so in production the region move was the bigger
  single lever.** Each iad1↔eu-west Supabase call measured **~250 ms** —
  worse than raw inter-region RTT, i.e. there is per-call gateway/TLS
  overhead on top — so even 7 batched stages stayed above 2 s. Co-locating in
  dub1 collapses per-call cost to milliseconds, at which point the
  parallelization is what keeps the total at ~0.6–0.7 s.
- **Locally the parallelization alone gave −38% on both routes** (per-call
  cost from the dev Mac ~170 ms and no region to fix) — exactly the
  signature the owner's local≈prod comparison predicted.
- **The compass score route is a clean control**: untouched by Fix 1, it did
  not move with parallelization (1,668 → 1,663) and halved with the region
  move (→ 657).
- **Remaining ~0.6 s residue**: the client's RTT to the edge, plus the
  Next.js middleware's own `auth.getUser()` (one Supabase Auth call that runs
  near the *user*, not in dub1, so it still pays a user↔eu-west leg on every
  API request), plus ~7 × milliseconds of now-local database work.
- p95 on the Fix-1-only row got *worse* for /complete (4,038) — consistent
  with parallel bursts opening multiple TLS connections cross-region on early
  cycles; it disappears in dub1 (1,553).

`latency-local-parallel.json`, `latency-prod-parallel.json` (Fix 1),
`latency-prod-dub1.json` (Fix 1+2).

## Part 4 — Backend completions (Priority 3)

### 4.1 §13.5 gate-state instrumentation (migration 023)

The Age-Bracket Transition Rule has three gates (G1 mean score ≥ 85% over the
3-session window; G2 top-tier response share ≥ 70% in every window session;
G3 zero retakes in the window) plus a chronological age floor and a 3-session
cooldown. The blueprint's §13.5 requires a threshold-validation trigger:
*"revisit the thresholds if none of the first 50 children clear all three
gates."* That was previously uncomputable — gate outcomes weren't stored.

Now: `session_instances.age_gate_evaluation` (jsonb, migration
`20260905000023`) is written on **every** evaluation (not just transitions):

```json
{ "gates": { "g1Mean": bool, "g2TopTier": bool, "g3NoRetakes": bool },
  "transitioned": bool, "blockedByCooldown": bool,
  "blockedByAgeFloor": bool, "windowSize": int }
```

The trigger query:

```sql
select count(distinct child_id) as children_evaluated,
       count(distinct child_id) filter (where (age_gate_evaluation->'gates'->>'g1Mean')::bool
         and (age_gate_evaluation->'gates'->>'g2TopTier')::bool
         and (age_gate_evaluation->'gates'->>'g3NoRetakes')::bool) as children_clearing_all_gates
from session_instances where age_gate_evaluation is not null;
```

### 4.2 Phase 10–12 zero-direct-placement — proven structural, not a defect

The evaluation had flagged that no child is ever *directly* placed into
Phases 10, 11 or 12 by the Compass. Proof (full version in
`phase-10-12-reachability.md`):

- The §6.2 decision tree is evaluated in order. **Phase 7's predicate accepts
  an unconditioned expressive band of [35, 55]** and **Phase 9's predicate
  accepts an unconditioned expressive floor of ≥ 55** — between them they
  partition the entire upper expressive axis *before* the Phase 10/11/12
  checks are reached. The late-phase predicates are therefore **shadowed**:
  no score profile survives to them.
- Phases 10–12 remain reachable two ways: via the **ELSE branch**
  (nearest-phase-by-driver-distance can select them) and via **RL
  advancement** through the curriculum.
- The engine transcribes §6.2 **faithfully** — the shadowing is a property of
  the blueprint's predicate ordering, not an implementation bug. Re-ordering
  or conditioning the predicates would change clinical placement behaviour:
  it requires explicit owner/SLP sign-off and a Compass `schema_version`
  bump, and was deliberately **not** done.

## Part 6 — The "Ife" advancement question — not a bug

Owner report: *"Ife is in Phase 11 and has passed all the sessions but she
has not been leveled up. why?"*

Diagnosis from her actual attempt history in Phase 11, in chronological
order: **75% (pass) → 85% (pass) → 65% (fail → retake) → 85% (pass) →
95% (pass)**.

Advancement requires **three consecutive passes at ≥ 75%**. The 65% attempt
was a fail and reset the consecutive run to zero. Her trailing run is
therefore **2 of 3** — one short. The engine is behaving exactly as
specified; one more standard pass at ≥ 75% advances her to Phase 12. No code
change was made or needed.
